# Red-team A: card lifecycle and engine logic (plano-rev80.md)

Method: walked one card through every state and transition, with the founder's commands, the timers and a crash at each boundary between "agent answered" and "state written". DBOS claims were checked against docs.dbos.dev (URLs at the end) and Hermes `-z` behavior against the local source (analise2/src/hermes-agent). Line numbers refer to plano-rev80.md. Known holes K1-K23 are not repeated; "fix-of-K#" marks a flaw in a chosen fix. Nothing outside redteam-A/ was written and no founder system was touched.

### A-1 · "Pronta" can carry stale inputs: order edits, non-urgent DECs and adjustments during a run have no freshness check · critical
- Scenario: E1 (Caio: 10 people × hours × US$0.50) is `pronta`. The founder taps the one-tap correction ("são 15 pessoas"), answers with a DEC not marked urgent, or sends "Pedir ajuste" while E2 runs. E1 stays `pronta` with 10; E5 reads the new order plus E1's old numbers; E2 finishes on its old package and passes validator and reviewer. The card arrives `pronta` with mixed assumptions and no flag.
- Why the plan misses it: "Card pronto nunca usa informação velha | Sim | Sim | Sim" (237), but the only mechanisms are "Se uma seção aprovada mudar depois, as partes que a usaram são refeitas" (212) and the urgent-DEC replan (316). DECs are "lidas na hora em que cada etapa começa" (316): checked at the start, never at the end. The "versão do card" (243) is a write lock, not an input check, and the mid-run edit is promised: "correção em um toque" (335).
- Fix: each execution stores `entradas_hash` (order-fields version + DEC/ajuste ids and versions received + hashes of upstream deliveries consumed). The transition function refuses `validação→revisão`, `revisão→pronta` and card→`pronta` if it differs from the hash recomputed now; mismatch sends the etapa to `na_fila` with `motivo=entradas_mudaram` (not rework) and bumps `execucao_n` (fences the old run). One column, one comparison.
- Proving test: the table-walk adds events {editar_ordem, novo_DEC, ajuste} at every state and asserts no path reaches `pronta` with a stale hash; end-to-end sim: approve E1, change 10→15, run E5, then E1 re-runs or the card parks.
- Phase: 2

### A-2 · The table that "proves everything" is not total: 6+ waiting conditions, all founder commands and 2 owners live outside it · high
- Scenario: an implementer builds the table from line 196 (5 working states + 3 finals + 2 parkings; the picture on 216 says "7 estados"). The doc adds outside it: card "congela" (244), "quarentena" (296), "esperando capacidade" (293), an agent paused by the "disjuntor" (199), a read-back before the card exists (99), etapas split or substituted (280, 289). Each becomes a flag in code with no exit, owner or deadline. The walk covers answer type, crash, repeated delivery and expired deadline only: no approve/ajuste/cancel/edit/answer/undo, no 80%/due/+1h timers, no parking default.
- Why the plan misses it: "nenhuma fica parada sem dono" (218); "percorre todas as combinações possíveis: cada tipo de resposta de agente em cada passo, queda do servidor no meio, entrega repetida e prazo esgotado" (242). Invariants speak of "card" (101, 228) while states belong to "etapa" (196), and "dono" is undefined for `aguardando dependência` and `validação`.
- Fix: write the table as data: (estado, evento, papel) → (novo estado, dono, prazo, conta?, bump de `execucao_n`). Map extras onto existing states with `motivo`/`bloqueio`: quarentena = `em_resolução`; capacidade/disjuntor = `na_fila` + `bloqueio` + `retomar_em`; read-back = `esperando_você` (rascunho); split/substituted = `cancelada` + `motivo` (A-5); "congela" dropped (A-11). Owners: aguardando_dep → Helena; na_fila/executando → agent; validação → "motor"; revisão → reviewer; esperando_você → founder; em_resolução → Helena, then founder.
- Proving test: the build fails unless every (estado × evento) pair is an edge or an explicit "proibido"; asserts every non-terminal state has owner and deadline, every terminal has out-degree 0.
- Phase: 2

### A-3 · fix-of-K12: dedup IDs do not exist on the queue type the plan needs, and SQL-side heals fail in four silent ways · high
- Scenario: "1 ou 2 cards por agente" (204) plus the 3-task cap of test 6 (439) needs one queue partitioned by agent (`partition_concurrency` + `global_concurrency`). DBOS docs: "Deduplication is not supported on partitioned queues." One queue per agent keeps dedup but loses the cap and priority across queues (5 × 2 = 10 Hermes vs 3 tested; I found no cross-queue limit or priority in the docs, so the order in 298 cannot be expressed). On any queue, dedup blocks while ENQUEUED/DELAYED/PENDING, so a stranded row holds the ID and the vigia gets `DBOSQueueDeduplicatedError` (caught as "já tratado": card stuck, silent). A SQL-side enqueue without partition key stays ENQUEUED forever; without `app_version` it goes only to the "latest" version (client docs); without priority it ranks HIGHEST, above Helena's intake.
- Why the plan misses it: "Filas por agente, limite de vagas, prioridade, novas tentativas e prazos já vêm prontos" (19); "as filas têm limite de vagas, prioridade e limite por agente" (541). K12 depends on dedup, and the text of the DBOS post on SQL-side enqueue names only workflow name, queue name, inputs and workflow ID (its signature is an image I could not read).
- Fix: one partitioned queue (key = agent), no dedup. Idempotency = `workflow_id = etapa_id:execucao_n` (a repeated ID returns the existing workflow). Heal = transition `reenfileirar(etapa)` that bumps `execucao_n` (fences the zombie, 231) and enqueues the new ID with explicit queue, partition key, priority, version. Vigia: ENQUEUED older than 2 min; PENDING with a version different from the current one.
- Proving test: same ID twice gives one run; kill mid-run, heal twice: one extra run, old write refused; enqueue without partition key: alarm within 5 min; `global_concurrency=1`, low-priority A + high-priority B: B first (cross-partition priority is undocumented, so measure).
- Phase: 2

### A-4 · "Free" retry classes have no ceiling, timeouts have no row, and the agent can pick its own failure class: silent quota burn · high
- Scenario: a Clara etapa needs 14-16 min against the 15-min kill. "a etapa volta para a fila" (141) and the failure table (278-287) has no "tempo esgotado" row; if it lands in "Queda do servidor: a etapa é refeita sem gastar tentativa" (294) it loops forever, each lap spending ~15 min of the company's single ChatGPT account (451). The etapa changes state every lap, so "etapa parada há mais de 1 hora" (461) never fires; the 429 row has no end either. A poison input that kills the engine loops until DBOS's recovery cap, then sits in MAX_RECOVERY_ATTEMPTS_EXCEEDED (never named in the plan) while our row says `executando`.
- Why the plan misses it: "Falha do provedor ou do servidor não gasta tentativa nem pune o agente" (239); "Espera e tenta de novo, com intervalo crescente | Mais de 1 hora: painel" (282). Classifying "pelos próprios sinais (código de saída...)" (291) fails with `hermes -z`: exit 2 means provider failure, iteration-budget stop and partial turn alike (hermes_cli/oneshot.py:92); and action 5 lets the agent name the type: "O tipo da falha, que dispara o manual de falhas" (135).
- Fix: every free class gets two ceilings (N laps, H hours), then `esperando_você` with the cause. Add the row "tempo esgotado = tentativa do agente: 1 retry com +50% de tempo, depois divide". Classify from `hermes -z --usage-file` (`turn_exit_reason`, `failed`, `partial`). "Registrar falha" offers only {não consigo, faltam dados, fonte inacessível}, always counted. Vigia: more than 8 executions of one etapa, or DBOS ERROR/MAX_RECOVERY_ATTEMPTS_EXCEEDED under an `executando` row.
- Proving test: sim modes `trava_20min`, `morre_sempre`, `429_sempre` leave the loop within the ceilings and the phone gets an alert; a provider-error text with exit 2 and a max-turns stop are classified differently.
- Phase: 2

### A-5 · Terminal-without-success does not propagate to dependents, parents, children or the plan · high
- Scenario: the founder cancels E3, acknowledges a failure on E1, or a sub-card ends cancelled. E5 stays `aguardando dependência` on an upstream that can never be `pronta`; the parent waits for a dead child; cancelling a parent with live children collides with "só fecha depois de todos os sub-cards". Only the card deadline (205) eventually calls Helena, and E5 (the founder's checklist) never appears. Run-time plan edits ("ajustar o plano" 197, "Divide a etapa" 280, "substitui a missão" 289) skip the check that runs only on activation; when an adapted plan fails, the stock roteiro silently wins.
- Why the plan misses it: "O card pai espera todos voltarem" (203) and "O card pai só fecha depois de todos os sub-cards" (233) are silent on a child that ends cancelled or failed; "Todo plano da Helena é checado ao ser ativado" and "Se não passar, vale o roteiro original" (210), with no word to the founder.
- Fix: when an etapa or sub-card enters `cancelada` or `encerrada_com_falha`, the same transaction (a) cancels its non-terminal children, (b) moves each direct dependent and the parent to `esperando_você` with options {pular, refazer, cancelar o card} and the standard parking default, (c) re-runs the activation check on any plan mutation and parks the card instead of using the stock roteiro. Vigia: no etapa in `aguardando_dep` with a terminal-not-`pronta` upstream.
- Proving test: walk every terminal × dependent state: dependent parked within 1 s; cancel a parent with 2 running children: children cancelled, no write accepted; sim Helena returns a cyclic plan: card parked with the reason shown.
- Phase: 2

### A-6 · Final states are not final: "Pedir ajuste" and the K14 undo need an edge out of `pronta` or `cancelada`, and the screen he approves may be stale · high
- Scenario: the returned card offers "Aprovar, Pedir ajuste e Usar como exemplo" (331) but no state is named for "returned, waiting for his verdict". If it is `pronta`, then "Pedir ajuste" (a counted backward move, 214) and the undo of a cancel (K14) leave a final. He may also approve on a screen opened before a section was redone (212), and the approval lands on the new delivery.
- Why the plan misses it: "Finais de verdade são só três: pronta, cancelada, ou encerrada com falha que você reconheceu" (196) vs "pedido de ajuste" in the rework counter (214); the version check (243) guards writes, not what he saw.
- Fix: finals have out-degree 0. `pronta` ends the card; "Aprovar" is an event row, not a state; "Pedir ajuste" (or undoing a cancel) after a final creates a NEW card with `origem_id` and the old deliveries as input, through the existing card-creation path. Every founder command carries `(card, versão vista, entrega_hash vista)`; a mismatch is refused with a visible message.
- Proving test: assert out-degree 0 for the 3 terminals; sim: Pedir ajuste on `pronta` leaves the old card untouched and creates a linked child; approve with a stale hash is refused.
- Phase: 2

### A-7 · Rework counter: limit never stated, counts the founder's own adjustments, and sits among 8 other counters with no single bound · high
- Scenario: the founder asks for three adjustments. The same counter takes his "pedido de ajuste" and "No limite, o card vai para em resolução"; there Helena substitutes the mission up to 2 times, so an LLM rewrites his order, and if he is away the default is "externo: cancela". The number is never given. Eight other limits (formato 2, revisor 2, dividir 2, passos 2, site 3, JSON 1 from K13, disjuntor 3, quarentena 2) have no stated precedence or reset, so the walk cannot prove termination.
- Why the plan misses it: "Toda volta para trás soma no mesmo contador: devolução do revisor, devolução a quem pediu, pedido de ajuste e substituição. No limite, o card vai para "em resolução"" (214); "a Helena substitui a missão até 2 vezes antes de chamar você" (289); "externo: cancela" (196); limits on 280, 281, 283, 284, 285, 199, 296.
- Fix: founder commands never touch the machine counter (they open a new `rodada` and reset it). One hard cap per etapa, `execucoes_do_agente ≤ 6`, counting author and reviewer runs for any reason, then `esperando_você` (not a Helena loop). Cap "substituição" at 1. The build also checks that every directed cycle in the transition graph contains an edge tagged `conta`.
- Proving test: property test over random event sequences (founder events included): agent runs per etapa stay ≤ cap and the walk terminates; DFS cycle check on the table.
- Phase: 2

### A-8 · "Toda mensagem vira exatamente um card" is not enforced: redelivery, "conversa", the classifier fallback and the read-back all escape it · high
- Scenario: (a) the protocol number is made on receipt, so a webhook redelivery or a double tap gives two inbox rows and two cards. (b) A real request labeled "conversa" has no card, owner or deadline; only the echo can reveal it. (c) During a quota outage, when classification fails most, his "sim, pode seguir" to a pending question becomes a NEW card asking him to pick a service, while the real question runs toward its default. (d) The read-back has no card, owner, deadline or vigia cover while it waits. (e) A rephrased request makes a second card and double research.
- Why the plan misses it: "Toda mensagem sua é gravada pelo código antes de qualquer IA, com número de protocolo" (105); "Se ela falhar duas vezes, o código cria o card com o seu texto" (105); "antes de criar o card" (99); "Toda mensagem sua vira exatamente um card ou entra num card existente" (238) vs the label "conversa" (105).
- Fix: `UNIQUE(canal, id_externo)` (WhatsApp message id; app = client uuid). The read-back creates the card at once as `esperando_você` (rascunho) with the standard parking. The fallback never creates a work card: it files "mensagem sem classificar", shown first in the app and alarmed after 30 min; free text never answers or cancels without the classifier. "Conversa" stays listed as "sem card" for 24 h. At creation, code lists open cards with the same empresa + roteiro and asks "Juntar com X?".
- Proving test: replay one webhook payload 3×: one row; fail the classifier twice with a pending question and send "sim": no new card, question still pending; an unclassified message older than 30 min shows in the vigia; two near-identical requests trigger the merge prompt.
- Phase: 2

### A-9 · Cancel does not stop the running work: DBOS acts only at the next step and the plan only ignores the late write · high
- Scenario: the founder cancels a card whose Clara etapa is mid-run (up to 15 min, 25 searches). DBOS `cancel_workflow` "preempts its execution (interrupting it at the beginning of its next step)", "Python provides no way to preempt a running synchronous function", and a one-step workflow has no next step. The Hermes process keeps spending the single ChatGPT quota and holds one of 3 slots; three cancelled cards idle the engine for 15 min; children keep running into a dead parent (A-5).
- Why the plan misses it: "Uma execução antiga ou cancelada não tem como escrever, e o tempo esgotado encerra o processo inteiro do agente" (247): the write is blocked, and the kill exists only for the timeout (141, 21).
- Fix: the step's wait loop (the one that already enforces max time) polls `cancelar_pedido`/`execucao_n` every ~5 s and kills the whole process group (`start_new_session=True` + `killpg`, so K1's stdio servers die too). One loop = timeout + cancel + fence.
- Proving test: sim `lento` (sleeps 10 min): cancel at t=20 s, process tree gone in under 15 s, slot free, no write accepted; a timeout kill leaves no grandchildren (`pgrep`).
- Phase: 2

### A-10 · fix-of-K14: the undo of an LLM-classified cancel or answer contradicts final states and cannot unwind what already ran · high
- Scenario: "cancela a parte do preço, mantém o resto" (WhatsApp) is labeled "cancelamento": the card goes `cancelada`, the process dies (A-9), partial work and quota are gone. The echo offers an undo, but (i) `cancelada` has no outgoing edge, (ii) on WhatsApp the "desfazer" reply is classified by the same LLM, (iii) for "resposta a uma pergunta" the DEC has already entered later steps and may have triggered the urgent replan.
- Why the plan misses it: "A Helena só classifica cada uma em: card novo, ajuste de um card, resposta a uma pergunta, cancelamento ou conversa" (105); "As decisões são lidas na hora em que cada etapa começa" (316); "a resposta vira uma decisão DEC e entra no contexto de todas as tarefas seguintes" (314).
- Fix: free text may only propose the two destructive labels (cancelamento, resposta). The echo carries a short code; the action runs when he taps in the app or replies exactly `OK <código>` or `DESFAZER <código>`, parsed by code. The app's cancel button stays direct. "Card novo" and "ajuste" apply at once.
- Proving test: 30 ambiguous phrasings (partial cancels, forwarded third-party text with imperative verbs): none changes a state without the code; `DESFAZER` within the window reverses a new card.
- Phase: 2

### A-11 · fix-of-K12/K17: "congela" has no state or exit, one bad rule freezes everything, and nobody watches Supabase or the scheduled job that runs the vigia · high
- Scenario: (1) a new SQL rule with a false positive (after any migration) freezes every open card: in-flight writes are refused, alerts repeat every 5 min, and a frozen card is not a state, with no unfreeze command, owner or deadline. (2) K17's "resumo diário como batimento" needs him to notice an absence, and the summary needs Helena's quota. (3) A paused or unreachable Supabase, or a failing scheduled job (the plan names no mechanism for the 5-minute check), silences the only watcher: 449 covers the VPS dying, not the database, and nothing on the VPS alerts when the DB is gone.
- Why the plan misses it: "Se alguma falhar, aquele card congela, a luz fica vermelha e você é avisado. Nunca em silêncio." (244); "Se o servidor inteiro cair, você fica sabendo." (449).
- Fix: drop "congela" in phase 2 (agents have no external tools, so freezing buys little): the vigia flags and alerts once per (card, rule), again every 6 h; new rules run 24 h in observation mode first. Add an external dead-man's switch pinged by the vigia every 5 min through pg_net (a free healthcheck-style service alerts the phone on silence) and an engine-side ntfy when the DB is unreachable for more than 2 min or the vigia's heartbeat row is older than 15 min. Add a rule: DB size above 70% of 500 MB.
- Proving test: disable the scheduled job: phone alert within 15 min; revoke the engine's DB role: ntfy from the VPS within 3 min; deploy a deliberately wrong rule: 0 cards frozen, 1 alert.
- Phase: 2

### A-12 · fix-of-K11: one entry point and 16 paused agents leave requests with nowhere to go, and v1 spends the same quota unseen · high
- Scenario: K11 says v1 takes no new missions while v2 serves 5 agents. He asks for iGreen/Saúde/eLiving work that needs a paused agent: v1 refuses, v2 has no service, the fallback asks him to pick from a menu that lacks it, the card parks and the default fires (external: cancel). ### A-13 · Parked waits: answer-versus-timer race, and "segue a recomendação" executes LLM-written text · medium
- Scenario: (1) he answers at 23:59:50; the default fires at 00:00:00 and cancels; his answer meets a final state and is refused, the DEC lost or half-written. (2) For `em_resolução` (reached after two rejected rounds, 285/214) the "recomendação" is Helena's free text and can read "entregar assim mesmo", which breaks "passou pelos portões". (3) If a default is stored as a DEC, the company memory holds a decision he never made.
- Why the plan misses it: "um padrão que você aprova antes (interno: segue a recomendação e avisa; externo: cancela)" (196); "Toda entrega aprovada passou pelos portões do seu serviço" (236); "a resposta vira uma decisão DEC" (314).
- Fix: a closed list of defaults per parking type, none of which approves a delivery: internal = keep waiting, remind at 24 h and 48 h, then cancel; external = cancel. Timer and answer use the same transition with the version check (first writer wins); a late answer to a defaulted parking opens a new card pre-filled with it and says so in the app.
- Proving test: walk both orders (answer then timer, timer then answer) for each parking × class; assert no DEC from a default and no `pronta` reachable from a default.
- Phase: 2

### A-14 · fix-of-K2: no version policy, and stranded PENDING rows silently consume the global slots · medium
- Scenario: DBOS defaults the version to a hash of workflow source, "only recovers workflows whose version matches", and "any PENDING workflow on the queue counts toward [global_concurrency], including workflows from previous application versions". A deploy that changes workflow code while steps run strands them: with `global_concurrency=3` every slot is held by rows nobody will recover, the engine stalls and the heal (A-3) cannot enqueue. If the version is pinned instead, reordering steps without `DBOS.patch` breaks replay of in-flight workflows. Rollback also needs `DBOS.set_latest_application_version`.
- Why the plan misses it: "Versão do motor fixada, mudanças entrando por chaves de compatibilidade do próprio DBOS" (62) vs "refeitas sem gastar tentativa, sempre na versão em que nasceram" (409): the latter needs a process running the old code (DBOS docs), which wait-then-replace does not give; "Voltar versão: publicar a etiqueta anterior" (410).
- Fix: pin `application_version` explicitly (a constant bumped only for a breaking change of workflow shape); one function per step type (shape-stable); the deploy script refuses if any PENDING/ENQUEUED row has another version; the rollback script calls `set_latest_application_version`. The same query is a vigia rule.
- Proving test: amend test 4: publish with a renamed step while a step is in flight, the card completes or is healed once; pre-fill 3 old-version PENDING rows: vigia alert within 10 min and the deploy script refuses.
- Phase: 2

### A-15 · fix-of-K1: crash points between "agent answered" and "state written" are not ordered; evidence, replay and the next enqueue can each be lost · medium
- Scenario: (1) Hermes exits, the engine dies before the checkpoint: the step re-runs (quota ×2); if only the engine process died, the first Hermes may still run on a profile or snapshot path keyed per etapa. (2) Checkpoint saved, but K1's snapshots are local files uploaded later: a publish recreates the container, the validator finds no page, every quote fails and the agent is charged "formato errado". (3) Transition committed, next workflow not yet enqueued (two systems, no shared transaction): the etapa sits `na_fila` with no workflow until the vigia heals it (5 min or more, and only if A-3 works). (4) If run and write share a step, a replay can give a different answer than the stored one while the validator reads the in-memory copy.
- Why the plan misses it: "retoma do último passo concluído e refaz o que estava pela metade; a gravação final usa chave única, então nada se duplica" (245) covers only duplicate writes; "quedas entre cada gravação" (249) runs on a simulator whose answers never change between calls; "somem quando ele é republicado" (381).
- Fix: Step A = run Hermes, upload snapshots to Storage under `execucao_id/` (unique per attempt), return the answer. Step B = read the answer back from the row stored under `etapa:execucao_n`, validate, transition. Missing evidence is an engine fault (free, 1 retry), not an agent strike. A trigger on `etapas` (estado → `na_fila`) enqueues via DBOS's SQL `enqueue_workflow` (atomic with the caller's updates per the DBOS post; spike the arguments first), else the vigia heal. Engine start kills stray `hermes` processes.
- Proving test: a "mutating simulator" (new answer on every call) with `kill -9` hooks after exit, checkpoint, upload, validate, commit and enqueue: one stored answer, validated == stored, one next workflow, zero agent strikes.
- Phase: 2

### A-17 · The "5 ações" are only the author's alphabet; failures have two names and three retry counts (fix-of-K13) · medium
- Scenario: reviewers return approve/reprove per criterion, Helena has "três coisas", the founder has his own commands; none is one of the 5. A plain "feito!" is "formato errado" (retried twice) or "sem ação", which has no row in the failure table and may fall into "Falha desconhecida", which stops the etapa at once; K13 gives one format retry, test 5 allows at most 1. The question after the per-card limit has no outcome. The walk over "cada tipo de resposta" cannot be built without an (estado, papel) matrix.
- Why the plan misses it: "Na v2 ele tem só 5 ações que mudam um card" (127); "A Helena decide só três coisas" (197); "marca aprovado ou reprovado em cada critério" (258); "é a falha "sem ação"" (141) vs "Formato errado ... ### A-18 · Deadline events have no once-only record: every scan can re-fire them, and the Helena call is pointless in the common case · medium

### A-19 · fix-of-K10: "provado = o que roda" holds only if nobody edits production by hand, and check-then-apply races a live inbox · medium

### A-20 · fix-of-K23: "America/Sao_Paulo em todo lugar" is not the default of any scheduler involved · low

## DBOS checks asked for in the brief, and sources
- Does a step's own timeout kill a sync subprocess? No. A step `timeout_seconds` exists only for async steps; "Python provides no way to preempt a running synchronous function"; workflow timeouts and `cancel_workflow` act "at the beginning of its next step". The kill at max time (141, 247) and on cancel must be coded in our step; no listed test exercises it (A-9 test).
- Dedup semantics: one workflow per `deduplication_id` per queue while ENQUEUED, DELAYED or PENDING; a collision raises `DBOSQueueDeduplicatedError` (or returns the existing workflow with `duplication_policy="return-existing"`); the ID is released when the workflow completes; unsupported on partitioned queues; behavior after ERROR or CANCELLED is not stated; the text of the SQL-side enqueue post does not mention it (A-3).
- Scheduled workflows after downtime: the docs present backfill as opt-in (`automatic_backfill=True`, or `backfill_schedule` by hand) and do not state the default for a deploy-time gap, so treat missed ticks as lost; one worker runs each fire; UTC unless `cron_timezone` is set. A table-scanning tick (K2) recovers by itself; once-a-day and once-per-level events do not (A-18, A-20).
