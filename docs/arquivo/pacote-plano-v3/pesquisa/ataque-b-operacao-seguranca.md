### B-1 · Phase 0 closes two ports but never checks whether v1 was already taken over, nor the rest of the surface · critical
- Scenario: Ports 9119 (dashboard) and 8642 (API server) of v1's Hermes have been public. Hermes' own docs say unauthenticated public dashboards and API servers were the entry point of the June 2026 campaign that planted SSH-key backdoors and persistent MCP config (HA:website/docs/user-guide/docker.md:175); the dashboard offers env read, config write, file write and a PTY (HA:hermes_cli/web_routers/config_env.py:117,259; files.py:834; chat_ws.py:538) and basic-auth is "Not suitable for direct public-internet exposure" (docker.md:148). v1's version, hence whether the dashboard failed closed, is unknown. If anything was planted, deleting the port mappings leaves the attacker inside a box that holds the ChatGPT grant, every profile .env and the VPS that will also host v2 (v1's earlier HTTP 429s fit someone else spending the subscription through 8642: inference, check the sessions DB). Docker-published ports bypass ufw ("Packets are routed before the firewall rules can be applied", docs.docker.com/engine/network/packet-filtering-firewalls), so EasyPanel :3000, Evolution, the Gateway or a DB port may be open too.
- Why the plan misses it: "Você remove as duas no EasyPanel e eu confiro de fora" (L58); "A v1 não é tocada." (L22); "A troca das chaves que apareceram no chat fica para o fim dos testes, como combinamos." (L441).
- Fix: Phase 0 step zero, read-only, one pasted block in the container console and one on the host, output pasted back as data: authorized_keys (root, hermes user, bind-mounted homes), each profile's mcp_servers/hooks/cron/skills against the expected set, files newer than the last deploy, `ss -tlnp`, docker.sock mounts, recent logins, Hermes sessions the dispatcher did not create. One full 1-65535 scan from outside plus a request to every EasyPanel domain; weekly connect-check of the sensitive ports from an Actions job. Any doubt: rebuild v1's container from a clean image, new ChatGPT device login, rotate everything (B-3) before Phase 2.
- Proving test: the outside scan shows only the intended ports; the compromise script's clean output is attached to the Phase 0 gate; the weekly job fails when a test port is re-published.
- Phase: 0

### B-2 · fix-of-K5: rail functions, the X-ray and sign-up remain reachable through the public anon key · high
- Scenario: ids-app ships the Supabase anon key (public by design). "By default, any role can run a database function ... including anon", and a SECURITY DEFINER function "can return rows the caller isn't allowed to read" (supabase.com/docs/guides/database/functions); sign-ups default to on (supabase.com/docs/guides/local-development/cli/config). Anyone can call `/rest/v1/rpc/<fn>` on any function in an exposed schema (default `public`, where the ~38 existing guard functions presumably live) and on every new rail function, or sign up and become `authenticated` (policies written for the role, not the founder's uid, expose everything). A transition or approval function that does not check the caller lets an outsider cancel or advance cards; the X-ray reads the `dbos` schema, which invites exposing it. Dated trap: on 2026-10-30 Supabase stops auto-granting new `public` tables to the Data API on existing projects (supabase.com/changelog/45329-breaking-change-tables-not-exposed-to-data-and-graphql-api-automatically; functions are not mentioned), so a migration tested before that date can behave differently after it.
- Why the plan misses it: "O card só muda de estado por uma única função do banco, que confere a tabela de passagens permitidas e a versão do card." (L243) checks table and version, never the caller; "O raio-X lê essas gravações" (L208).
- Fix: every migration revokes EXECUTE on all functions from public, anon, authenticated, then grants only to the motor role, or for the few app-called ones to authenticated with an in-function `auth.uid() = <founder>` check (approvals also `aal2`, i.e. TOTP on the founder account); SECURITY DEFINER with `set search_path = ''`; `rail` and `dbos` outside the Exposed schemas, the app reads thin `api.*` views; Storage buckets private with signed URLs; sign-ups and anonymous sign-ins off; explicit GRANTs in the same migration (valid before and after Oct 30). Audit the existing 38 functions now.
- Proving test: CI calls every function of every schema with the anon key and with a non-founder sign-up token and expects 401/403/permission denied; a catalog query fails the build if any function grants EXECUTE to PUBLIC or anon outside an allowlist file.
- Phase: 0 (audit existing functions, sign-up setting), 2 (new ones)

### B-4 · Supabase Free is a hard 500 MB cliff that also disables the in-database alert; capacity is never measured or tested · high
- Scenario: Free = 500 MB database, 1 GB Storage, 5 GB egress, no daily backups, pause after a week (supabase.com/pricing). Above 500 MB the project goes read-only and "all write operations are blocked — including background jobs, scheduled tasks" (supabase.com/docs/guides/platform/database-size): DBOS cannot checkpoint, the card-state function cannot move a card, and the vigia and its pg_net alert cannot write, so the system stops with the only designed alarm behind the closed door; deleted rows do not shrink usage until vacuum. Growth is real: DBOS stores each workflow's input/output and each step's output in `dbos`; steps here carry deliverables up to 8,000 characters plus fields and "o pedido original ... inteiro" (L107, L312); "a conversa completa de cada execução" (L381) has no stated home or size; open-source DBOS has no automatic retention (policies are a Conductor feature, docs.dbos.dev/conductor/retention; the library has `DBOS.delete_workflow(id)` only). The size of v1's 61 tables and the tier are unknown.
- Why the plan misses it: "o plano grátis do Supabase tem 500 MB ... histórico do motor com prazo de guarda" (L61); "e que o Supabase comporta o histórico" is listed as an unproven base assumption (L12), yet none of the seven tests (L28-36) nor the gate "A fase 2 só termina quando os 6 primeiros testes abaixo passam." (L24) covers it; "O painel do DBOS é pago e não faz falta." (L542).
- Fix: Phase 0: one read-only query from the founder's PC session (DB size, ten biggest relations, Storage use, plan tier) becomes the baseline. Decide Free vs Pro explicitly: Pro from US$25/month gives 8 GB, 100 GB Storage, daily backups kept 7 days, no pausing (supabase.com/pricing), removing the cliff, the pause, the backup gap (B-10) and most retention work, and is not a paid model API, so DEC-014 stands. If Free stays: steps return ids/hashes (full text stored once, in our table or Storage), a nightly DBOS scheduled workflow calls `delete_workflow` on completed runs older than N days, and the motor itself reads `pg_database_size` hourly and alerts directly at 70% (350 MB) and on SQLSTATE 25006 "read-only transaction".
- Proving test: new Test 8 in the Phase 2 gate: 72-hour soak at target load with real-size payloads, MB per card measured, projected days to 350 MB >= 60 with the purge on; in the CI Postgres run `alter database ... set default_transaction_read_only = on` and assert the motor's direct alert reaches the phone within 5 minutes.
- Phase: 0 (measure, decide), 2 (soak)

### B-8 · fix-of-K1: `buscar` and `ler_pagina` are server-side fetchers with no SSRF defence · high
- Scenario: The K1 tools run inside the motor's container on the same Docker host as Evolution, the Gateway, ids-app and EasyPanel, return the body to the model and save it as a snapshot the founder later sees and Storage keeps. A planted page, search result or redirect can point them at `http://127.0.0.1:...`, a sibling service by name, the host gateway (EasyPanel's panel), `http://169.254.169.254/` (metadata and user-data on many VPS providers), `file://` (if a browser-based fetcher is used), a hostname that resolves public at validation and 127.0.0.1 at connect (rebinding), or a 10 GB body. No tool beyond the legitimate fetcher is needed, and the response comes back as "evidence" in a card and in Storage: internal service content or metadata credentials disclosed, or the motor starved.
- Why the plan misses it: "Quem lê páginas da internet só pode entregar ou registrar falha" (L448) limits what the agent does next, not where the fetcher connects; "Toda citação precisa existir, palavra por palavra, na cópia da página que o agente leu" (L257) turns whatever the fetcher returned into evidence.
- Fix: one `safe_fetch()` for both tools: http/https and ports 80/443 only; resolve DNS once and connect to the validated IP; refuse loopback, link-local, RFC1918, CGNAT, ULA and the Docker bridge/host gateway; re-validate every redirect (max 5); cap body (2 MB) and time (20 s); allow-list content types; no cookies or auth headers; strip invisible Unicode before saving (B-9).
- Proving test: SSRF corpus in the simulator battery on every build: 127.0.0.1, localhost, [::1], 0.0.0.0, decimal/octal/hex IPs, 169.254.169.254, 10./172.17./192.168. ranges, `evolution` and `helena-gateway` names, `file:///etc/passwd`, ports 22/5432/6379, a redirect to each, a DNS name flipping to 127.0.0.1, a 100 MB stream: all refused or truncated, reported as a failure type, never as page content.
- Phase: 2

### B-11 · fix-of-K12/K2: old-version workflows stranded by a deploy hold queue slots and dedup keys, so the vigia's re-enqueue does nothing · high
- Scenario: A redeploy or crash loop leaves step workflows ENQUEUED/PENDING under the old `application_version`. DBOS recovers only workflows whose version matches the running code (docs.dbos.dev/python/tutorials/upgrading-workflows), so they never run again, yet "any `PENDING` workflow on the queue counts toward the limit, including workflows from previous application versions" and a workflow that is enqueued, delayed or executing holds its deduplication ID (DBOSQueueDeduplicatedError) (docs.dbos.dev/python/tutorials/queue-tutorial); starting a workflow with an existing ID returns a handle to the existing one instead of a new run (docs.dbos.dev/python/tutorials/workflow-tutorial). So K12's re-enqueue is a no-op, or reports success on the stranded row; the card waits "na fila" until L461 speaks an hour later, the global slot stays taken, and each deploy leaves more strays.
- Why the plan misses it: "As que forem interrompidas são refeitas sem gastar tentativa, sempre na versão em que nasceram." (L409) is possible only while an old-version process lives, but a single-service redeploy replaces it; test 4 asserts "Nenhum card perdido ou duplicado" (L33), not that queue capacity and dedup keys are released.
- Fix: workflow ID and dedup ID = f(card, step, attempt), `attempt` stored in our table; a boot-time reconcile before the queue starts lists ENQUEUED/PENDING/DELAYED rows whose version differs from the current one and cancels them (`cancel_workflow`; `fork_workflow(..., application_version=current)` where a step must continue), deletes them later, and the vigia re-creates the step with attempt+1 without charging a retry; prefer `worker_concurrency` over a global limit; informational alert when reconcile cancels more than 0.
- Proving test: extend test 4: kill mid-step, redeploy with a changed version, then assert (i) no ENQUEUED/PENDING/DELAYED row with the old version after boot, (ii) queue capacity equals the configured value, (iii) the vigia produced exactly one running workflow per interrupted step, (iv) valid final state and no duplicate delivery; repeat 5 deploys in a row and assert capacity does not decay.
- Phase: 2
